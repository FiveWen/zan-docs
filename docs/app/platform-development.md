# 平台型 App 开发流程

本流程由我方商城团队执行。

## 1. 协议评审

先确认平台身份、站点范围、SDK 加载、登录凭据、能力列表和回调语义。没有服务端校验方案时不能只依赖客户端返回值建立商城登录态。

## 2. 登记接入方

为平台分配稳定的 `hostApp` key，并配置允许的 `siteId`、Adapter 和声明能力。入口示例：

```text
/mall/?siteId=<站点ID>&hostApp=<平台key>
```

`hostApp` 是候选宿主标识。运行时还必须探测真实 Bridge；不能仅凭 URL 参数清理网页登录态或调用平台登录。

## 3. 实现 Adapter

Adapter 负责把统一能力映射到平台协议，至少实现登录。分享、扫码、定位、导航和支付按需求及平台真实能力选择性实现。具体接口见 [Adapter 规范](/app/platform-adapter)。

## 4. 对接商城登录

标准链路为：

1. Adapter 从平台取得临时凭据；
2. Mall/Ucenter 调用商城后台进行验证和账号映射；
3. 校验返回的站点、用户和 token；
4. 两个项目分别同步提交自己的会话；
5. 登录完成后才开放其他原生能力。

过期登录响应不能覆盖较新的会话。写入一半失败时应清理本次会话，不能留下 token 与用户信息不一致的状态。

## 5. 接入业务能力

页面只调用统一能力，不直接引用平台全局对象。能力不可用时应降级到原网页逻辑或给出明确提示，不得伪造成功。

## 6. 跨项目与生命周期

Mall 跳转 Ucenter 时透传非敏感宿主上下文。页面刷新、返回、进入后台再恢复时，都需要重新确认当前上下文仍然有效。离开宿主场景时清理监听器和临时状态。

## 7. 验证与上线

- 平台 App 主流程：登录、分享、扫码、支付或其他本次能力；
- 取消、超时、SDK 缺失、后台登录失败和重复点击；
- Mall ↔ Ucenter 往返及 401 恢复；
- 普通浏览器、微信、小程序和历史 App 回归；
- 灰度开关、日志和可恢复的回滚方案。

完成双方真机验收后再发布公共包和升级业务项目依赖。
